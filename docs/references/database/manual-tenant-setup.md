# Manual Tenant Setup — DBA Operational Guide

**Audience:** DBAs provisioning a new company account + first admin user.
**Status:** Authoritative. Replaces any prior Spring auto-bootstrap path.
**Last updated:** 2026-05-11.

---

## 1. Why this exists

The WeCMS refactor (`wecms-api/`) no longer auto-creates company / admin / employee / link rows at startup. The previous `BootstrapRunner` was removed; production / UAT / local startup never writes tenant data on its own. New tenants are provisioned **exclusively** by DBAs running a manual SQL script against the target database, following the legacy WeCMS / JexFrame operational pattern.

The Spring login flow (`AuthService.login`) reads pre-existing rows from `USER_INFM`, `USER_BUSI_CONN_INFM`, `BUSI_INFM` and `BUSI_ADMN_INFM` — it does not depend on any startup-time creation. As long as the rows produced by the manual SQL match the schema and the password is in a Spring-readable format (see §4), login Just Works.

Two target databases have meaningfully different requirements; **pick the script that matches your target**:

| Target | Schema flavour | Uses `hash()` / `encrypt()` ? | Audit columns | Script to use |
|---|---|---|---|---|
| Legacy DEV / UAT (`https://test.wecms.vn`) / PROD (`https://www.wecms.vn`) | Legacy JEX schema | Yes — `public.hash(text)` + `public.encrypt(text)` installed in those DBs | `varchar(14)` `yyyyMMddHHmmss` strings | **Script A** (§6) |
| Refactor LOCAL (`localhost:5434/wecms_dev`) | Modern PostgreSQL types | **No** — those legacy functions are not installed locally and will not be added (per the "DB Function Policy" rule in [wecms-api/CLAUDE.md](../../../CLAUDE.md)) | `TIMESTAMPTZ` / `DATE` native types | **Script B** (§7) |

**Important:** these scripts target two different schemas. Running Script A against the local DB will fail (no `hash()` / `encrypt()` functions; varchar timestamps don't cast to `TIMESTAMPTZ`). Running Script B against UAT will fail (text passwords / phones aren't in the format legacy code expects). Pick the right one.

## 2. Table reference — what each row means

| Table | Purpose | Required for login? |
|---|---|---|
| **`BUSI_INFM`** | Company / tenant master. One row per company, PK = `BIZ_KEY` (shape `{NTNL_CD}_{CHNL_ID}_{NNNNNN}`, e.g. `VN_VNM0004_000018`). Carries display name (`CMPN_NM`), product type (`PRDT_TYPE`), national / channel codes, status flags. | **Yes** — `AuthService.me()` reads it to surface `CMPN_NM` in the session. |
| **`EMPL_INFM`** | Employee master, scoped to the company. Composite PK `(BIZ_KEY, EMPL_NO)`. `EMPL_NO` is a per-tenant monotonic id of shape `YYYYMMDD_NNN` generated by `wb_get_next_val`. Carries HR-style data: department, position, phone, email, address. | **No** — login does not read `EMPL_INFM`. A user can log in with `USER_BUSI_CONN_INFM.EMPL_NO = NULL`. The row is required for HR / payroll / employee-management surfaces (most of which are not yet ported to the refactor). |
| **`USER_INFM`** | Globally-unique user master. PK = `USER_ID` (typically the user's email). Carries `USER_PW` (hashed), display name, contact info, account flags (`ACTV_YN`, `LOCK_YN`, `DEL_YN`). Same `USER_ID` is shared across all companies the user belongs to. | **Yes** — `AuthService.login` first reads this row by `USER_ID`. |
| **`USER_BUSI_CONN_INFM`** | Many-to-many link between users and companies. Composite PK `(USER_ID, BIZ_KEY)`. `DEL_YN` makes links soft-deletable. **Note**: current WeCMS operation expects one user = one active company; multi-company links are an exceptional path (see §10). | **Yes** — `findAllByUserIdAndDelYn(userId, 'N')` resolves which BIZ_KEY the JWT is issued for. |
| **`BUSI_ADMN_INFM`** | Per-company admin master. Composite PK `(BIZ_KEY, USER_ID)`. **Presence = ADMIN** of that company; **absence = USER**. Legacy `USER_BUSI_CONN_INFM` has no `AUTH_GR_CD` column (confirmed via DEV `information_schema`), so this table is the authoritative authority source. | **Yes** — `existsByBizKeyAndUserId(bizKey, userId)` resolves the `authGrCd` JWT claim. |

**Insert order matters** for FK constraints:

```
BUSI_INFM  →  EMPL_INFM  →  USER_INFM  →  BUSI_ADMN_INFM  →  USER_BUSI_CONN_INFM
```

- `EMPL_INFM` references `BUSI_INFM(BIZ_KEY)`.
- `BUSI_ADMN_INFM` references both `BUSI_INFM(BIZ_KEY)` and `USER_INFM(USER_ID)`.
- `USER_BUSI_CONN_INFM` references both `BUSI_INFM(BIZ_KEY)` and `USER_INFM(USER_ID)`; `EMPL_NO` is optional (nullable, no FK).

## 3. Required flags & audit columns

| Flag | Required value for a normal active admin | Notes |
|---|---|---|
| **`USER_INFM.ACTV_YN`** | `'Y'` | `'N'` → login rejected with `WBE1010` (account inactive). |
| **`USER_INFM.LOCK_YN`** | `'N'` | `'Y'` → login rejected with `WBE1011` (account locked). |
| **`USER_INFM.DEL_YN`** | `'N'` | `'Y'` → login rejected with `WBE1128` (account deleted). |
| **`USER_BUSI_CONN_INFM.DEL_YN`** | `'N'` | `'Y'` → the link is invisible to `findAllByUserIdAndDelYn`; effectively no active link. |
| **`BUSI_INFM.DEL_YN`** | `'N'` (legacy) — nullable on refactor | Soft-delete flag. |
| **`BUSI_INFM.BUSI_STTS`** | `'N'` (NORMAL) | Legacy post-auth gates exist but are deferred in the refactor (no `BUSI_STTS` check currently fires). |
| **`BUSI_INFM.PRDT_TYPE`** | `'F'` for WeCMS default, `'M'` for WeCMS Lumens, `'H'` for HAENGSUNG Electronics, etc. | One letter. Refactor enum (`PrdtType`) recognises **only `F`, `M`, `H`** today; other legacy letters (`W`, `R`, `B`, `E`, `U`, `L`, `S`, `P`, `C`, `D`, `T`) round-trip through wire / JWT but no behaviour is gated on them. See [wecms-api/CLAUDE.md](../../../CLAUDE.md) §"Product-type rule". |
| **`BUSI_INFM.NTNL_CD`** | `'VN'` for Vietnam | NOT NULL; default `'VN'`. |
| **`BUSI_INFM.CHNL_ID`** | `'VNM0004'` (the channel id for the Vietnam WeCMS instance) | Part of the BIZ_KEY shape. |

**Audit columns** (every table):

| Column | Legacy UAT type | Refactor LOCAL type | What to put |
|---|---|---|---|
| `REG_ID` | `varchar(100)` | same | `'SYSTEM'` for DBA-created tenants, or the DBA's user id |
| `MOD_ID` | `varchar(100)` | same | usually same as `REG_ID` at creation time |
| `REG_DTM` | `varchar(14)` `yyyyMMddHHmmss` | `TIMESTAMPTZ` | see scripts below |
| `MOD_DTM` | `varchar(14)` | `TIMESTAMPTZ` | see scripts below |

## 4. Password handling

Spring login (`WecmsPasswordEncoder` + `LegacyHashPasswordEncoder` + `AuthService.login`) verifies the supplied password against `USER_INFM.USER_PW` by **re-hashing the input and comparing**. The stored value is never decrypted (passwords are one-way hashes, not reversible encryption).

| Format | Detection | Where it comes from | Supported by Spring login? |
|---|---|---|---|
| **BCrypt** | starts with `$2a$` / `$2b$` / `$2y$`, length 60 | Spring's `BCryptPasswordEncoder` (strength 10) | ✅ Preferred. All new account writes from the refactor go through `PasswordHashService.encodeForNewUser(...)`. |
| **Legacy SHA-256 base64** | 44-char Base64, no `$` prefix | `public.hash(text)` PL/pgSQL function: `encode(digest(text, 'sha256'), 'base64')`. Installed in legacy DEV/UAT/PROD only. | ✅ Read-only path. `LegacyHashPasswordEncoder` replicates the algorithm in Java for verification (constant-time compare). |
| **Sentinel `__BCRYPT_PENDING__`** | literal exact-string match | Flyway seed migrations on local R&D (V2 / V5 / V10 / V73) | ⚠️ **Local profile only.** `DataSeeder` (`@Profile("local")`) runs at startup, finds rows whose `USER_PW = '__BCRYPT_PENDING__'`, and replaces each with `BCrypt("Password!1")`. After that one-time patch, the user logs in with `Password!1`. **Never use this sentinel on UAT/PROD** — DataSeeder does not run there. |
| Anything else (plain text, MD5, raw SHA-1, …) | — | — | ❌ Never matches. Login fails. |

### Auto-upgrade on successful login

After a successful `passwordEncoder.matches(rawPw, storedHash)`, if `storedHash` is not already BCrypt, `AuthService.login` (line ~94 of the file) re-encodes and rewrites `USER_INFM.USER_PW` with a fresh BCrypt hash. The original legacy SHA-256 row is replaced; subsequent logins use BCrypt. This is the documented "transparent SHA-256 → BCrypt upgrade" path.

**Operational implication for ops:** if the refactor is ever deployed alongside the legacy JEX system against a shared DB, this auto-upgrade would silently break legacy login for upgraded users (legacy code only knows the 44-char SHA-256 format). Today this is a non-issue — refactor is local-only R&D — but document this if/when coexistence becomes real.

## 5. Phone / sensitive-field encryption

Legacy DEV/UAT/PROD store some fields as **reversible symmetric ciphertext** via `public.encrypt(text)` (typically `pgp_sym_encrypt`-based) — usually `USER_INFM.CLPH_NO`, `EMPL_INFM.CLPH_NO`, `EMPL_INFM.EMER_CLPH`.

| Environment | `encrypt()` available? | What to insert |
|---|---|---|
| Legacy DEV / UAT / PROD | ✅ yes — installed in those DBs | `encrypt('+0084...')` — the legacy JEX code path decrypts on read |
| Refactor LOCAL | ❌ no — never installed, will not be added (DB function policy) | Plain text (e.g. `'+0084...'`) **or** `NULL`. The refactor entities map `CLPH_NO` as a plain `String`; the auth flow does not read this column at all. |

**Login is not affected** by phone encryption either way — `AuthService.login` reads only `USER_ID`, `USER_PW`, `USER_NM`, and the flag columns. Any sensitive-field-display surface that ports to the refactor would need either a Java port of `encrypt`/`decrypt`, or plain-text local data, or to accept that legacy ciphertext is opaque in the refactor.

## 8. How Spring login resolves a manually-created user

Once the manual SQL has committed, the user can log in with no further setup. `AuthService.login(req, ip, langCd)` performs the following reads:

1. **`USER_INFM.findById(USER_ID)`** → must exist; otherwise `WBE1009`.
2. **Flag gates** on the loaded `USER_INFM` row:
   - `DEL_YN = 'Y'` → `WBE1128` (deleted)
   - `ACTV_YN = 'N'` → `WBE1010` (inactive)
   - `LOCK_YN = 'Y'` → `WBE1011` (locked)
3. **`passwordEncoder.matches(raw, USER_PW)`** → uses `WecmsPasswordEncoder`, accepts BCrypt OR legacy SHA-256 base64. Mismatch → `WBE1009`.
4. **Optional transparent upgrade** — if `storedHash` is not BCrypt, rewrite `USER_PW` with a fresh BCrypt hash. The row's `MOD_ID` becomes the user's own `USER_ID`, `MOD_DTM` auto-updates.
5. **`USER_BUSI_CONN_INFM.findAllByUserIdAndDelYn(USER_ID, 'N')`** → must return at least one row. Empty → `WBE1009`. One row → auto-pick (normal path). Two or more → chooser response (exceptional path; see §10).
6. **`USER_BUSI_CONN_INFM`** `LST_LGN_DATE` updated on the resolved link.
7. **`BUSI_INFM.findById(bizKey)`** → reads `CMPN_NM` (for sidebar display) + `PRDT_TYPE` (for the JWT claim).
8. **`BUSI_ADMN_INFM.existsByBizKeyAndUserId(bizKey, userId)`** → `true` ⇒ `authGrCd = "ADMIN"`, `false` ⇒ `"USER"`.
9. **JWT issued** with claims `{ sub: userId, userNm, bizKey, langCd, authGrCd, prdtType }`.
10. **`USER_LOGIN_HIS`** SUCCESS row written.

Logout (`POST /api/v1/auth/logout`) is a stateless stub — the frontend clears the JWT; backend writes nothing.

## 9. Verification queries

Run after the manual SQL to confirm everything is in place. Replace the example `BIZ_KEY` / `USER_ID` values with the ones you just inserted.

```sql
-- (a) Company exists with the expected product type

  FROM busi_infm

-- (b) Employee exists

  FROM empl_infm

-- (c) User exists with login-ready flags
SELECT user_id, user_nm,
       LEFT(user_pw, 4) AS pw_prefix, LENGTH(user_pw) AS pw_len,
       actv_yn, lock_yn, del_yn
  FROM user_infm
 WHERE user_id = 'NuApartment_LOCAL@gmail.com';
-- Expected: 1 row; actv_yn='Y', lock_yn='N', del_yn='N';
--   pw_prefix = '$2a$' / '$2b$' / '$2y$' (BCrypt)
--      OR     = '__BC' (sentinel, local profile only — restart Spring to patch)
--      OR     = any 4 chars with pw_len = 44 (legacy SHA-256 base64 — Script A only).

-- (d) Admin authority exists
SELECT biz_key, user_id, user_nm
  FROM busi_admn_infm
 WHERE biz_key = 'VN_VNM0004_000018'
   AND user_id = 'NuApartment_LOCAL@gmail.com';
-- Expected: 1 row → user is ADMIN of this company.

-- (e) User-company link exists and is active
SELECT user_id, biz_key, empl_no, del_yn
  FROM user_busi_conn_infm
 WHERE user_id = 'NuApartment_LOCAL@gmail.com';
-- Expected: 1 row; biz_key matches the new company, del_yn='N'.

-- (f) Full login-readiness one-liner (returns 1 if everything is in place)
SELECT
    COUNT(*) FILTER (WHERE u.del_yn='N' AND u.actv_yn='Y' AND u.lock_yn='N')      AS user_ok,
    COUNT(*) FILTER (WHERE ubc.del_yn='N')                                         AS conn_ok,
    COUNT(*) FILTER (WHERE bi.biz_key IS NOT NULL)                                 AS company_ok,
    COUNT(*) FILTER (WHERE adm.user_id IS NOT NULL)                                AS admin_ok
  FROM user_infm u
  LEFT JOIN user_busi_conn_infm ubc
         ON ubc.user_id = u.user_id
        AND ubc.biz_key = 'VN_VNM0004_000018'
  LEFT JOIN busi_infm bi
         ON bi.biz_key = ubc.biz_key
  LEFT JOIN busi_admn_infm adm
         ON adm.biz_key = ubc.biz_key
        AND adm.user_id = u.user_id
 WHERE u.user_id = 'NuApartment_LOCAL@gmail.com';
-- Expected: all four counters return 1 → user can log in as ADMIN of this company.
```

## 10. Known limitations & caveats

| Topic | Limitation |
|---|---|
| **`hash()` / `encrypt()` legacy DB functions** | Only present in DEV / UAT / PROD. **Never installed on the refactor LOCAL DB** — the "DB Function / Legacy Function Policy" rule in [wecms-api/CLAUDE.md](../../../CLAUDE.md) forbids adding new legacy PL/pgSQL helpers. Script A will not run against LOCAL. |
| **`__BCRYPT_PENDING__` sentinel** | Only works under the Spring `local` profile (`DataSeeder` is `@Profile("local")`). Production / UAT / staging deployments must use Option 2 (pre-computed BCrypt hash) instead. |
| **Auto-upgrade of legacy SHA-256 to BCrypt on login** | Currently always-on in `AuthService.login`. Acceptable for local R&D. If the refactor is ever deployed to coexist with legacy JEX on the same DB, this must be gated off — a BCrypt-encoded `USER_PW` cannot be validated by legacy JEX login. |
| **One user = one company account (operational rule)** | Current WeCMS operation treats a `USER_ID` as belonging to exactly one active `BIZ_KEY`. The refactor has chooser infrastructure that handles ≥ 2 active links, but this is **not** an officially supported production pattern — it exists as a safe fallback only. Do not derive business requirements from the chooser's existence. If a real multi-company rule lands later, the relevant docs (here + CLAUDE.md) must be revised. |
| **`EMPL_INFM` not required for login** | Login reads only `USER_INFM`, `USER_BUSI_CONN_INFM`, `BUSI_INFM`, `BUSI_ADMN_INFM`. A user can log in with `USER_BUSI_CONN_INFM.EMPL_NO = NULL`. The `EMPL_INFM` row is required by HR / payroll / employee-management modules (most not yet ported to the refactor). For minimum-viable login, you could skip Steps 3 and 4 — but provision the employee row anyway so HR features work when they land. |
| **Phone ciphertext (legacy)** | Refactor has no equivalent of `public.encrypt(text)`. Legacy DEV-imported users carry encrypted CLPH_NO blobs that the refactor cannot decrypt. Login does not read CLPH_NO, so this has zero impact on auth — but any future feature that displays a phone field will see opaque text for legacy-imported users. |
| **Hibernate `validate` mode** | The refactor runs `spring.jpa.hibernate.ddl-auto = validate`. New columns or column-type changes must go through Flyway. The manual scripts here do not add columns; they only insert rows into existing tables — so they don't trigger validation issues. |
| **Flyway "no edit applied migration" rule** | Strictly enforced. Manual SQL is not a Flyway migration — it does not record in `flyway_schema_history` and is not idempotent against re-runs (unless you wrap each `INSERT` with `ON CONFLICT DO NOTHING`). For repeated/scripted local setup, prefer a real Flyway migration (V73 is the working template). |

## 11. Quick reference — when to use what

| Situation | What to do |
|---|---|
| Provisioning a new UAT or PROD customer | Script A (legacy schema, `hash()` / `encrypt()`, varchar-14 timestamps) |
| Adding an R&D tenant to your local DB for development | Write a new Flyway migration following the V73 pattern. **Manual SQL is a fallback only.** |
| One-off local DBA insert without a migration | Script B, Option 1 (sentinel + restart) for convenience, or Option 2 (pre-computed BCrypt) for repeatable scripts |
| New customer on `PRDT_TYPE = 'H'` (HAENGSUNG-tier) | Either script; change exactly the one PRDT_TYPE line |
| Resetting a forgotten admin password on UAT/PROD | `UPDATE USER_INFM SET USER_PW = hash('newpass'), MOD_DTM = to_char(...) WHERE USER_ID = '...'` |
| Resetting a forgotten admin password on LOCAL | `UPDATE USER_INFM SET USER_PW = '__BCRYPT_PENDING__' WHERE USER_ID = '...'` then restart Spring (local profile only) |
| Deactivating a user | `UPDATE USER_INFM SET ACTV_YN = 'N', MOD_DTM = ... WHERE USER_ID = '...'` — next login fails `WBE1010`. |
| Removing a user from a company (soft delete the link) | `UPDATE USER_BUSI_CONN_INFM SET DEL_YN = 'Y', MOD_DTM = ... WHERE USER_ID = '...' AND BIZ_KEY = '...'` |
