01 — Banking Overview

Purpose, scope & status 개요

Purpose. The Banking module is the cash-visibility and money-movement core of WeCMS — it lets a company see real-time balances across every connected bank account, drill into the transaction ledger, classify and reconcile each transaction, move funds between its own VND accounts, and produce daily-cash / financial / cash-flow reports. Bank connectivity is live: balances and transactions are scraped from the banks through the Coocon / NXiSAS smart gateway.

Scope. Five business domains, all inside the single wecms-api Spring Boot deployable plus the wecms-web Next.js client: Current & Savings (VND), Current & Savings (FCY), Internal Transfer (VND), Reports (Daily Cash · Daily Financial · Cash Flow), and Smart Organizer. Bank Credentials & live scraping support all of them.

Current status. Account Inquiry (VND + FCY), Transaction History (VND + FCY), Own Account Transfer, Transfer History, Smart Organizer and all four reports are migrated and wired full-stack; SIT/UAT verification is complete for the inquiry/history/transfer/organizer features. Reports call the legacy DB functions directly (no Java recompute on the active path).

Refactor north-star. Preserve legacy JEX behavior — the refactor reproduces what JEX does column-for-column against the live JEX DB; it does not redesign it. New identifiers are kebab-case slugs (banking-account-inquiry-vnd), never legacy WSVC ids.

  • Login. The user authenticates; the JWT carries the tenant (bizKey), authority (authGrCd = ADMIN/USER) and product type (prdtType = F/M/H). Every banking call reads identity from this signed token via TenantContext — never from request input.
  • Account Inquiry. Banking lands on the account list. The backend resolves currency scope and per-user account authority (ACCT_AUTH_INFO) and returns balances + totals from ACCT_MSTR.
  • Balance Verification. "Update balance" drives a live scrape (LOGIN → BALANCE → TRANSACTION jobs) through the Coocon/NXiSAS gateway; on success ACCT_MSTR balance + ACCT_TRNS_HSTR rows are refreshed.
  • Transaction Creation → Approval → Transfer. An own-account transfer is composed and validated, then the browser-driven engine executes it with a bank 2nd-factor; the bank itself is the approval authority — there is no in-app approval state machine for own-account transfers.
  • Result Processing. Spring records the final engine outcome as one immutable row in NAPAS_REMIT_TRNS_HSTR (idempotent on the supplied key).
  • Reporting. Confirmed ledger + classification data feed the four reports, computed by legacy PostgreSQL functions.

Foreign-currency handling

  • Multi-currency (FCY-A01). Lists every non-VND account (CCY_CD <> 'VND'); an in-page dropdown narrows to a concrete currency. Legacy was USD-only — that restriction was retired by PO direction.
  • Per-account scope (FCY-T01). Transaction History inherits the account's own ACCT_MSTR.CCY_CD; each account renders only its own currency's rows — no mixing, no cross-currency arithmetic.
  • Per-currency totals. The list response carries totals_by_ccy[]; a scalar "Balance" sum is meaningful only after narrowing to one currency.
  • Formatting. AmountFormatter.forDisplay(value, ccyCd) renders ₫ for VND, prefix symbols for USD/EUR/KRW/JPY, none for the rest.
  • Last-update source (FCY-A02). Online accounts read ACCT_HIS_LST_INQ_DT; FD-only banks fall back to ACCT_BAL_LST_INQ_DTM — mirrors legacy.

Exchange information & related services

  • FCY shares one code path with VND — a single AccountController / AccountService / TransactionService; the account resolves its own currency (no if (FCY) branch).
  • Exchange Rate Inquiry is a separate Payment-domain module; FCY screens display amounts in the account CCY and do not perform live conversion.
  • Smart Organizer match/unmatch is wired from FCY Transaction History (per-account scope, R11 fix).
  • View Setting screenIds: banking-account-inquiry-fcy + shared banking-transaction-history.
  • Export providers: AccountInquiryFcyExportProvider + TransactionHistoryExportProvider.

FCY — full-stack, SIT/UAT verified (5 blockers closed) As-of-date historical balances (OQ-FCY-2): live snapshot only; reconstruction deferred

06 — Internal Transfer (VND)

Own-account transfer & history 내부 이체

Move funds between the company's own registered VND current/saving accounts within the same tenant — SAME_BANK (same bank code) or NAPAS (cross-bank via NAPAS rails). Execution is browser-driven through the vendor-signed NXiSAS engine; Spring records the final outcome once, immutably. There is no in-app Pending/Approved state machine — the bank's own 2nd-factor + IB review is the approval.

Success

Row written to NAPAS_REMIT_TRNS_HSTR; audit SCRAPING_RESULT_OK (AUDIT_LOGS_INFM.WSVC_ID='own-account-transfer'). Response carries seq_no, bank_tx_id, trns_stts, status=success.

08 — Smart Organizer

Rule-driven bulk classification 스마트 정리

Transaction Data
ACCT_TRNS_HSTR (synced, unconfirmed)
→
Classification
LATERAL match to RMRK_ORG_INFM (R01)
→
Grouping
rule supplies proposal: direction · acct · purpose · VAS · contact
→
Organization
resolveRows() denormalizes codes → names (R07)
→
Display
review grid → bulk confirm → ACCT_TRNS_RCV_PAY_INFM

Purpose & user benefit

  • A single-account, rule-driven classifier that lists unconfirmed transactions matching a saved remark rule and pre-fills each with the rule's proposed classification.
  • Benefit: drastically reduces manual data entry for reconciliation — staff review and bulk-confirm instead of classifying row-by-row.
  • One screen serves both VND and FCY — currency is data-driven (R06), no code fork; the account's own CCY_CD drives amount formatting.

Logic

  • Rules in RMRK_ORG_INFM: remark pattern + MATCH_TYPE (Exact/Contains) + direction, prioritized by DISP_ORD.
  • Exact matches when remark is identical and direction aligns; Contains matches on case-insensitive substring regardless of direction.
  • Match runs as a SQL LATERAL sub-join (legacy correlated sub-query parity), tenant + account scoped (R11).
  • Confirm writes denormalized names (VAS + contact) to ACCT_TRNS_RCV_PAY_INFM (R05); RCV_PAY_SEQ_NO via wb_get_next_val.

APIs: GET /banking/smart-organizer/eligible · POST /banking/smart-organizer/confirm · rule CRUD GET|POST|PUT|DELETE …/rules + POST …/rules/reorder. Components: SmartOrganizerController / OrganizerRuleController + SmartOrganizerService / OrganizerRuleService + AccountAccessGuard + BankCdResolver. Migrations V172–V174. Legacy fnsh_0200_001/002. full-stack, SIT/UAT verified (6 blockers closed) drag-reorder save UI (SO-2) deferred

Authentication & authorization

  • JWT carries identity, tenant, authority and product type — signed and immutable; JwtAuthenticationFilter populates TenantContext per request and rejects revoked tokens.
  • Menu authz (F-3 live): every business endpoint is gated by @PreAuthorize("@menuAuthz.canAccess('<slug>')"). Access = product tree (F/M/H) ∩ USER_MENU_AUTH_INFM grants; admins get the full product tree but never bypass the product scope.
  • Frontend is never trusted — a direct endpoint call is gated server-side regardless of UI state.

Approval & transaction validation

  • Per-account authority: non-admins are filtered to their ACCT_AUTH_INFO V (view) / W (withdraw) grants; AccountAccessGuard enforces it on detail/transfer.
  • Transfer approval is the bank's own 2nd-factor (OTP/QnA) + IB review — there is no in-app approval state machine for own-account transfers; Spring records the final outcome only.
  • Transaction validation: own-account transfer runs the 7-step intake (idempotency, currency, type, amount, source, target, persist).
  • Coexistence: passwords stay legacy SHA-256 (verify-only, no write-back); bank certs use the legacy AES-256-CBC cipher.
⚠
Pre-deploy gates. R-02 (action-level R/D/T authorization) and R-03 (dispatch-callback network protection) do not block local R&D but block UAT/PROD. Bank scraping reaches the Coocon gateway; the in-memory token-revocation / rate-limit stores need a durable/multi-instance backing before a multi-instance deploy.
