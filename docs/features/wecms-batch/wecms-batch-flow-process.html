01 — Executive Overview

Purpose, scope & status 개요

Purpose. WeCMS Batch is the firm-banking dispatch engine — it delivers a committed WeCMS payment to the bank gateway (Coocon/EFS) and reconciles the outcome: building fixed-length deposit files, encrypting/signing envelopes, transferring over SFTP, processing inbound result callbacks, and writing the per-transfer and per-file audit trail.

Scope. Backend only, inside the single wecms-api deployable — there is no separate batch jar. Covers real-time transfer (EFS 202/204), file/bulk transfer (EFS 301/302 + callbacks), depositor inquiry (EFS 201), and the result-check sweep (EFS 203).

Current status. Code-complete and production-grade, but inert by default: six feature flags default OFF and the mock EFS/SFTP clients throw rather than fake success, so nothing dispatches until infrastructure is provisioned and SIT round-trips pass.

Refactor summary. A polling-based, JEX-runtime-coupled batch farm became event-driven Spring services. Real-time and bulk transfers fire on a Spring afterCommit hook; only the result-check sweep stays a scheduled job.

  • Payment Created → Approval Complete. Owned by the payment modules (internal-transfer, vendor, expense, payroll, overseas). Dispatch does not start until the payment is approved and committed.
  • DB Commit → afterCommit. The dispatch trigger is a Spring TransactionSynchronization that runs after the payment transaction commits — never inside its uncommitted state. This is the core change from legacy polling.
  • Dispatch Service → EFS/SFTP. Real-time targets call EFS directly; file batches build a fixed-length file, SFTP-upload it, then call EFS 301.
  • Callback → Status Update. File completion is driven by inbound gateway callbacks (01301 then 01302); real-time completion is the 202 response (or the 203 result-check sweep for no-response cases).

Success flow

9 → 6 → 0

RC 0000 → both TB_FIRM_TRAN and TB_PAY_TARGET set to 0 (U002). Balance (BAL_AMT) persisted from the 202 response.

Failure flow

9 → 6 → 3

Other RC → 3 FAIL. G999 no-definitive-response → EFS 203 recovery; if still unresolved the row stays at 6 for the result-check sweep.

Services & repositories

  • RealtimeDispatchRegistrar — registers the afterCommit hook.
  • RealtimeDispatchService.dispatch(bizKey,tranDt,tranSeq) — orchestration + status writes (@Transactional(REQUIRES_NEW)).
  • RealtimeTransferService.transfer(...) — EFS 204/202/203 calls.
  • TbFirmTranRepository.existsByTranDtAndBizKeyAndTranSeq(...) — idempotency guard.

DB writes & API calls

  • TB_FIRM_TRAN — insert at PROC_STAT=6 (TRAN_TP=202), update to 0/3.
  • TB_PAY_TARGET — updated to the same terminal value (0/3); FX columns on 204 success.
  • TB_FIRM_BAT_API_TRAN — per-leg API audit row.
  • EFS 202 (transfer), optional 204 (FX), 203 (recovery).

Split / branch division

Legacy C5: when TB_FIRM_CONF.BAT_TRAN_BRANCH_DIV='Y' and request count > limit, calculateBatchDivision splits into ceil(reqCnt/limit) files, each with its own round / FIRM_FILE_NM / MST / DATA / SFTP / 301. limit ≤ 0 degrades safely to a single file.

File generation & SFTP

Detail rows are Vietnamese-tone-normalized (VietnameseText.replaceTone) before encode. SFTP/EFS failure marks the file FAIL and breaks the per-file loop (legacy R004 parity) — never rethrown into the payment tx. The move step (to rdata/success) is best-effort.

Both callbacks are VV-verified before decrypt. A count/amount mismatch on 01301 marks the file FAIL (REG_RSLT_CD='9999') and suppresses the 302. Update Result

Cron

@Scheduled(cron="${wecms.dispatch.result-check.cron:-}", zone="Asia/Ho_Chi_Minh"). Default "-" = never fires. ~1 min when enabled.

Locking

@SchedulerLock(name="ResultCheckJob.run", lockAtMostFor="PT2M", lockAtLeastFor="PT5S"); JdbcTemplateLockProvider (.usingDbTime()) on the shedlock table.

Retry behavior

No per-row retry — a still-pending row stays at PROC_STAT='6' and is re-examined next tick. Selects today + > 2 min old.

⚠
Disabled by default. Do not enable before SIT validation. Known day-boundary edge case in the same-day + HHmmss filter — apply the timestamp-range fix before enabling the cron in PROD.

12 — EFS Integration Flow

The six gateway legs EFS 연동

All legs route through EfsApiClient.send(EFS_xxx, envelope) → /WGVN_EFS_xxx.jct. The request is an AES-256/CBC EV envelope + HMAC-SHA256 VV signature carrying the partner ID; the response carries a result code (FirmBankingResultCd). The real client activates only when efs.enabled=true; otherwise the mock throws.
